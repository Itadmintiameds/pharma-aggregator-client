Seller User Service — schema consolidation and deployment topology

What Seller User owns today across three parallel entity packages, how those collapse into one service schema, and why this service sits in the single-writer bucket rather than active-active.

01

Overview

Seller User owns the seller's identity end to end: profile, registration, onboarding documents, bank details, and the seller/coordinator auth surface that Order, Quotation, and Product all lean on to answer "is this seller allowed to act." Nothing about a seller's catalog or transactions lives here — only who they are and whether they're approved.

Traffic is bursty rather than steady: registration and document upload spike around onboarding windows (new seller cohorts, re-verification pushes) and go quiet in between. Document upload in particular is I/O heavy, not CPU heavy — the work is streaming files to S3 and writing metadata rows, not computation — so this service scales on request queue depth, not on CPU utilization. Sizing it like a compute-bound service would leave it either idle and over-provisioned or backed up during exactly the windows it needs to hold up.

Open question — tbl_terms_master is misplaced: it lives under entity/temp/seller today but its content (legal terms/conditions text) is shared, not seller-specific — Buyer registration presumably needs the same terms. It shouldn't ship inside Seller User's schema as-is; it belongs in a shared legal-content table, referenced by both Seller User and Buyer User rather than owned by either.
Three lifecycles, one schema: a seller record today moves through Temp → Pending → live Seller across three separate table families with independent primary keys. Consolidating into Seller User Service means picking a single seller identity that persists across all three stages (a state column, not three tables), rather than carrying the three-way split forward into the new service. This is a real migration task, not a rename — it touches every FK that currently points at whichever of the three tables a given feature happened to be built against.

Also flag: tbl_ifsc_overrides (bank-IFSC lookup) sits in its own entity/ifsc package today but exists purely to validate tbl_seller_bank_details/tbl_temp_seller_bank_details — no other domain reads it. It's a candidate to fold into Seller User's schema rather than staying a standalone package.

Both Seller User and Buyer User FK into shared master tables — tbl_state_master, tbl_district_master, tbl_taluka_master, tbl_seller_type_master/tbl_buyer_type_master, tbl_document_type_master. These stay a shared read-only reference module per the HLD, not a numbered service of their own, and get cached at the edge since they change on the order of months, not requests.

03

Communication

Seller User is called far more than it calls out — the dominant traffic pattern is other services asking "is this seller approved," not Seller User reaching into anyone else's data.

Sync Inbound eligibility lookups

on nearly every write path elsewhere
  • Order Management → Seller User: is this seller active/approved before accepting an order line against them.
  • Quotation Management → Seller User: same eligibility check before a quotation can be issued.
  • Product Management → Seller User: seller-approval check before a listing can be published or updated.
  • These are read-only and called at high frequency relative to Seller User's own write volume — they should be cached aggressively (short TTL, invalidated on approval-status change) rather than hitting the seller table on every call.

Platform Boot-time platform calls

on service startup, not business traffic
  • Registers itself with Discovery Service so Order/Quotation/Product can resolve it without hardcoded endpoints.
  • Pulls environment config from Config Service at boot — DB connection details, S3 bucket names, feature flags.
  • These are platform plumbing, not part of the seller-eligibility request path, and shouldn't be conflated with the sync business calls above.

Deployment

ECS Fargate for the API, Aurora PostgreSQL for the consolidated schema, S3 for document storage — the existing S3Service in the codebase already targets this pattern, so document upload doesn't need a new storage integration, just a new bucket and IAM boundary per service.

resource "aws_rds_cluster" "seller_user" {
  cluster_identifier      = "seller-user-${var.region_short}-${var.environment}"
  engine                  = "aurora-postgresql"
  engine_version          = "15.4"
  master_username         = var.db_master_username
  master_password         = var.db_master_password
  db_subnet_group_name    = var.db_subnet_group

06

Scaling & region topology

Seller User sits in the HLD's single-writer with warm standby bucket, not active-active — the opposite topology from Product/Search. That's a deliberate call, not a default.

Registration and auth are correctness-sensitive: two regions independently accepting seller registrations or issuing refresh tokens against divergent copies of tbl_seller/tbl_user creates split-brain identity data that's expensive to reconcile after the fact (duplicate sellers, conflicting approval states, tokens that don't match). Product and Search can run active-active because a stale read of a listing is cheap to tolerate and self-heals from an event stream; a stale or conflicting write to seller identity is not something that self-heals — it needs a human to reconcile. So the tradeoff here is deliberately correctness over read scale: one writer region, one warm standby.

Failover is a controlled Aurora promotion, not an instant DNS flip: the standby cluster is kept warm (replicating, right-sized, but not accepting writes), and a region failure triggers a runbook-driven promotion of the standby to writer, then a Route 53 cutover once promotion confirms healthy. This is minutes, not seconds — an acceptable cost for a service where accepting writes against an unpromoted, possibly-lagging replica is worse than a short outage.

07

Decisions worth writing down

Decision — one seller identity, three lifecycle states

Collapse Temp/Pending/Live into a single schema with a status column

The current tbl_temp_seller → tbl_pending_seller → tbl_seller chain is three tables with independent keys standing in for what is really one entity moving through registration states. Seller User Service should model this as one seller table (plus its child tables for documents/bank/address/coordinator) carrying a lifecycle_status enum, with history preserved in the existing tbl_seller_history/tbl_temp_seller_review_history pattern rather than in separate parallel tables per stage. This beats keeping three tables because every consumer of "give me this seller" currently has to know which of three tables to check depending on approval state — that branching logic disappears once there's one identity.

Decision — standardize on Buyer's per-domain auth pattern

Seller User should adopt dedicated auth tables, not keep sharing entity/auth

Today Seller reuses a generic tbl_user/tbl_refresh_tokens/tbl_signup_otp/tbl_login_otp package shared with coordinator login, while Buyer already has its own tbl_buyer_signup_otp, tbl_buyer_login_otp, tbl_buyer_refresh_tokens. Once both are separate services, a shared entity/auth package becomes a cross-service dependency that defeats the point of splitting them — Seller User would have to call into whatever owns the generic auth tables (or that package becomes an awkward third service) just to issue its own tokens. Recommendation: Seller User forks its own auth tables scoped to seller + coordinator logins, following Buyer's existing pattern, rather than the reverse. It's less churn overall — Buyer's pattern is already proven in production — and it keeps each service's auth data inside its own schema boundary, which is the whole point of the split.

Decision — fold IFSC overrides in, carve terms master out

tbl_ifsc_overrides moves into Seller User; tbl_terms_master moves to shared legal content

tbl_ifsc_overrides exists solely to validate Seller's bank-details entry and has no other reader — it belongs inside Seller User's schema rather than its own standalone package, so bank-details validation doesn't require a cross-service call for what is effectively a lookup table scoped to one feature. tbl_terms_master, despite living under entity/temp/seller today, holds legal content that Buyer registration will need too — it should not become part of either service's owned schema and instead move to the shared reference module alongside the state/district/document-type masters, read-only and cached the same way.
