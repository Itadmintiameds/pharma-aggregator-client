Order Management — the strict-consistency core of the order lifecycle

Why Order stays single-writer while everything around it scales out, what has to physically move out of its package before Billing can be its own service, and how quote acceptance, price checks, and event fan-out fit together in one request.

01

Overview

Order Management owns orders, order lines, order status transitions, and returns/refunds — the record of what a buyer actually committed to buy and what happened to it afterward. This is the one service in the platform where correctness has to win over horizontal write scaling.

Every other write-heavy service in the HLD (Product, Search) is built to scale writes out across regions because a stale read or a duplicated write is recoverable — you re-index, you re-sync, the buyer barely notices. An order is different: double-charging a buyer, losing a status transition, or accepting an order against stock that no longer exists is not a data-quality problem, it's a financial and regulatory one. So Order Management is deliberately built as a single-writer, strongly-consistent service even though that costs it the active-active write scaling other services get — see §6 and §7 below for how that trade-off is drawn.

02

Data ownership

The entity audit of the current monolith's entity/order package shows 8 tables: tbl_order, tbl_seller_order, tbl_order_item, tbl_order_status_history, tbl_return_request, tbl_refund, tbl_payment, and tbl_invoice.

The first six are squarely Order's: an order splits per seller (tbl_seller_order) since a single buyer cart can span multiple sellers, line items live under tbl_order_item, every status change is journaled in tbl_order_status_history rather than overwritten in place, and returns/refunds get their own request and settlement tables.

Flag — tbl_payment and tbl_invoice are misplaced today: both currently live inside Order's entity/order package, not a separate Billing package. This is not a labeling accident to fix with a rename — it's a required physical migration: the tables, their JPA entities, and the code paths that write them have to move into Billing's own schema and cluster before Billing can be extracted as an independent service. See the Billing Management doc's data-ownership section and ADR-004 for the no-duplication rule this migration exists to make enforceable.
03

Communication

Order sits at the center of the lifecycle: one synchronous call comes in from Quotation, one synchronous call goes out to Product, and two async event streams fan out to Billing and Notification.

Sync IN Quotation Management → Order

create-order-on-accept
  • When a buyer accepts a quote, Quotation calls Order to create the order before it returns "accepted" to the buyer.
  • This is a blocking dependency by design — the buyer must never see "accepted" for a quote that has no corresponding order.
  • The order references the quote by ID; nothing from the quote row is copied into Order's tables.

Sync OUT Order → Product Management

price/stock confirmation on order creation
  • Before accepting an order, Order confirms current price and stock with Product Management in the same request the buyer is waiting on.
  • Catalog data can drift between quote and purchase; this call is what stops an order from being confirmed against a price or stock level that's no longer true.

Async OUT Order → Billing Management

OrderCreated / OrderStatusChanged via EventBridge
  • Billing reacts to these events to generate invoices and track payment state — invoicing never blocks order confirmation.
  • Order has no knowledge of whether or when Billing finishes processing the event.

Async OUT Order → Notification Service

order-confirmation emails/SMS
  • Notification must never receive a synchronous call from any service, Order included — this is a platform-wide rule, not an Order-specific optimization.

05

Deployment

ECS Fargate for compute, Aurora PostgreSQL as a single-writer cluster — no multi-writer pattern, because strict consistency on order state is the whole point of this service.

modules/order-management/main.tf 
// single-writer Aurora — no aurora_replication_source_identifier fan-out,
// standby region is provisioned but not a second writer
resource "aws_rds_cluster" "order_db" {
  cluster_identifier      = "order-mgmt-${var.environment}"
  engine                  = "aurora-postgresql"
  engine_version          = "15.4"
  master_username         = var.db_master_username
  master_password         = var.db_master_password
  backup_retention_period = 7
  // var.standby_region provisions a warm-standby cluster via cross-region
  // snapshot replication, not a second write endpoint — see §6
}

resource "aws_rds_cluster_instance" "order_db_writer" {
  cluster_identifier = aws_rds_cluster.order_db.id
  instance_class     = var.db_instance_class
  engine             = aws_rds_cluster.order_db.engine
}

module "order_ecs_service" {
  source        = "../ecs-fargate-service"
  service_name  = "order-management"
  image         = "${var.ecr_repo_url}:${var.image_tag}"
  desired_count = var.task_count
  cpu           = 1024
  memory        = 2048
  autoscale_on  = "request_count"
}

variable "standby_region" {
  description = "region for warm-standby Aurora cluster; promoted manually on regional failover"
  type        = string
}
06

Scaling & region topology

Order runs single-writer with a warm standby per the region-topology rules in ADR-007 — explicitly not active-active.

A regional outage means a controlled Aurora promotion of the standby to writer, with an RTO measured in seconds to minutes rather than zero. That's an accepted cost: the alternative, an active-active writer topology, would mean resolving write conflicts on order and payment state across regions, and there's no conflict-resolution strategy for "which region's version of this order's status is correct" that doesn't risk the exact correctness failures this service exists to prevent.

07

Decisions worth writing down

Decision — Payment and Invoice must be physically extracted

tbl_payment / tbl_invoice move to Billing's own schema/cluster, not a shared table or a view

These tables sit in Order's package today purely as an artifact of the monolith's history, not because Order needs to own payment or invoice data. Extraction has to be physical — new schema, new cluster, code moved to Billing's service boundary — because a shared table or a read-only view would leave the door open for a cross-service join, which is exactly what ADR-004's no-duplication rule is designed to prevent. See the Billing Management doc for the migration plan.

Decision — Order stays single-writer while Product goes active-active

Order correctness outranks read/write scale here

Product Management can afford active-active because a stale product read is cheap to tolerate and easy to reconcile. Order cannot: two regions independently accepting writes against the same order would create exactly the double-charge and lost-status-transition failures this service is built to avoid. Per ADR-007, Order is bucketed with the single-writer-plus-standby services rather than the active-active ones, and that bucketing is a direct consequence of what "correct" means for an order versus a product listing.
