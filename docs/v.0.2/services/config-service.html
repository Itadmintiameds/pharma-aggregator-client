Config Service — externalized config, high availability over throughput

Per-service, per-environment, per-region configuration, pulled at boot and refreshed live without a redeploy — the thing that makes the platform's region rollout actually one-click instead of one-click-plus-manual-config.

01

Overview

Config Service externalizes configuration — per service, per environment, per region — out of application code and deploy artifacts. Every domain and platform service reads its config from here rather than from bundled properties files, which is what lets the same container image run unmodified in every region.

Traffic to it is low: a pull at boot, occasional refreshes after that. But it sits on the critical path at exactly the moments that matter most — every service's boot sequence blocks on it, and a live config refresh (a feature flag flip, a rate-limit change) depends on it being reachable. That combination means the design target here is high availability, not high throughput. A Config Service that's slow under load is a non-problem at this traffic level; a Config Service that's occasionally unreachable takes every dependent service's boot or refresh down with it.

02

Data ownership

No business tables. Config Service owns configuration key/value state — the AWS AppConfig application / environment / configuration-profile hierarchy — and points to Systems Manager Parameter Store for the plain (non-secret) values themselves.

Secrets are explicitly out of this store. Anything sensitive — database credentials, third-party API keys, signing keys — is pulled from AWS Secrets Manager, not stored inside Config Service or Parameter Store. This is a real security boundary, not an implementation detail: it means a Config Service compromise or a misconfigured read policy on it never exposes a secret, because secrets were never there to expose. Keeping this distinction sharp is worth stating plainly rather than letting "config" quietly become a place secrets accumulate over time.

03

Communication

Sync IN — from every domain and platform service, in two distinct patterns:

  • Boot pull (HTTP): a service starting up fetches its full config profile before it starts serving traffic.
  • Refresh event (webhook), not polling: when a config value changes, an event/webhook triggers a re-pull in already-running services. No service polls Config Service on a timer waiting for changes.

The refresh-event model is what makes the one-click region rollout in ADR-006 actually work without touching running services: rolling out a config change to a live region means pushing to AppConfig and letting the webhook fan out, not redeploying every service that reads that value. Polling would get the same eventual result far more slowly and with load proportional to service count; a push model keeps propagation fast and nearly free regardless of how many services are listening.

04

Architecture diagram

Config Service sits underneath the domain services, not inline with client traffic — matching the platform topology where Config and Discovery are infrastructure every service depends on at boot, not a stop on the request path. Edges run both ways: boot-pull up top, refresh-push back down.

05

Deployment

OptionChoiceOperational costWhy / why not
A managed AWS AppConfig + Systems Manager Parameter Store No cluster to run Chosen. The backend already deploys via ECS/ECR, so this needs no new deployment target at all — it's a set of AWS API calls the service SDK already knows how to talk to, per ADR-002.
B self-hosted Spring Cloud Config Server, Git-backed A stateful service to deploy, scale, and patch, per region Would work, but adds an entirely new component to operate — a Git-backed config server with its own HA story — purely to duplicate what AWS already runs as a managed service.
modules/config-service/main.tf 
// one AppConfig application per platform, one environment per deploy target, one profile per service
resource "aws_appconfig_application" "platform" {
  name = "pharma-aggregator"
}

resource "aws_appconfig_environment" "region_env" {
  application_id = aws_appconfig_application.platform.id
  name           = "${var.region_short}-${var.environment}"
}

resource "aws_appconfig_configuration_profile" "order_mgmt" {
  application_id = aws_appconfig_application.platform.id
  name           = "order-management"
  location_uri   = "ssm-parameter://${aws_ssm_parameter.order_mgmt_config.name}"
  type           = "AWS.Freeform"
}

resource "aws_ssm_parameter" "order_mgmt_config" {
  name  = "/pharma-aggregator/${var.region_short}/${var.environment}/order-management"
  type  = "String"
  value = jsonencode(var.order_mgmt_config_values)
  // secrets are never placed here — see Secrets Manager reference in the service's own config
}

One configuration profile per service, deployed alongside every other region's Terraform via the same module — a new region means a new environment inside the same AppConfig application, not a new system.

06

Scaling & region topology

Provisioned identically per region via the same Terraform module, matching ADR-006's one-click rollout pattern. There's no cluster to replicate here — AppConfig and Parameter Store are already regional AWS resources, so "add a region" is a Terraform apply with a new region variable, not a capacity-planning exercise.

Availability matters far more than latency for this service. A .cost-strip isn't meaningful here the way it is for a compute-heavy service — at this traffic level (occasional boot pulls, occasional refresh events), Config Service is nearly free. Stating that plainly is more honest than forcing stat tiles onto a service where the interesting number would just be "close to zero."

07

Decisions worth writing down

Decision — AWS-native over self-hosted Config Server

AppConfig + Parameter Store, no cluster to operate per region

AWS AppConfig and Systems Manager Parameter Store beat a self-hosted, Git-backed Spring Cloud Config Server because they need no new deployment target — the backend already deploys via ECS/ECR, and this rides the same AWS-native path. See ADR-002.

Decision — secrets never live in Config Service's own store

Secrets Manager is the only place secrets are read from

Plain configuration values live in AppConfig/Parameter Store; anything sensitive is pulled from Secrets Manager instead. This is a deliberate security boundary, not an oversight — it means a compromised or over-broadly-permissioned Config Service read path can leak configuration, but never credentials, keys, or tokens.
