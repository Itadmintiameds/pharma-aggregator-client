Discovery Service — the live registry that wires regions together

Who's up, in which region, at which address — the registry every service registers with and queries, and the actual mechanism (not just a principle) behind zero-manual-wiring region rollout.

01

Overview

Discovery Service is a live service registry: who's up, in which region, at which address, right now. Every service both registers with it on boot and queries it to resolve peers — there's no other source of truth for "where is Product Management's address in this region" anywhere in the platform.

As with Config Service, availability matters more than latency — a resolve query is cheap and infrequent per call, but a Discovery Service that's unreachable breaks every service's ability to find its peers, which cascades immediately. This is what makes "spin up a new region" actually wire itself together: a new region's services register themselves against that region's Discovery instance the moment they boot, and everything that needs to find them can, with nobody hand-editing an endpoint list anywhere.

02

Data ownership

No business tables. Discovery Service owns live service-instance registration state — AWS Cloud Map namespace / service / instance records.

This state is ephemeral and health-checked, not a durable database in the traditional sense. An instance that stops sending heartbeats drops out of the registry on its own; there's no row to migrate, back up, or reconcile the way there would be for an orders table. Stating this plainly matters because it's easy to reach for domain-service framing ("what's the schema, what's the retention policy") that simply doesn't apply — the registry's correctness comes from continuous health-checking, not from durability guarantees.

03

Communication

Platform IN, from every service:

  • Registration on boot — a service announces itself into the registry before it starts accepting traffic.
  • Deregistration on shutdown — a clean exit removes the instance immediately rather than waiting for a health check to time it out.
  • Continuous health-check heartbeat (gRPC/HTTP) — not a business call, but present on every service's boot and liveness path for as long as it runs.

Every service also queries Discovery to resolve peers for direct service-to-service calls — the canonical example is Order Management resolving Product Management's address to confirm price/stock. This query path is exactly what lets service-to-service calls bypass API Gateway entirely (see api-gateway.html): internal traffic never needs a public-facing router because it resolves its destination directly from the registry.

04

Architecture diagram

Same "platform sits underneath" layout as Config Service — Discovery is infrastructure every service depends on continuously, not a stop on the client request path. Edges run both ways: register/heartbeat flowing down, resolve-queries flowing down and answers flowing back up.

Deployment

OptionChoiceOperational costWhy / why not
A managed AWS Cloud Map (or ECS Service Connect if staying on plain ECS) No cluster to run Chosen. Integrates directly with ECS service discovery — the backend already deploys via ECS, so this is no new deployment target, per ADR-002.

modules/discovery-service/main.tf 
// one private DNS namespace per region; every service registers its instances into it
resource "aws_service_discovery_private_dns_namespace" "region" {
  name = "internal.${var.region_short}.pharma-aggregator"
  vpc  = var.vpc_id
}

resource "aws_service_discovery_service" "order_management" {
  name = "order-management"

  dns_config {
    namespace_id   = aws_service_discovery_private_dns_namespace.region.id
    routing_policy = "MULTIVALUE"
    dns_records { type = "A" ttl = 10 }
  }

  health_check_custom_config {
    failure_threshold = 1 // ECS reports task health directly; drop fast on failure
  }
}

One namespace per region, one aws_service_discovery_service per domain service registered into it — the same module runs for every region, just parameterized by region_short.

06

Scaling & region topology

Provisioned per region via the same Terraform module, matching ADR-006. Instances are health-checked continuously, so dead instances drop out of the registry automatically — nobody removes a stale endpoint by hand, and nobody adds a new one by hand either.

This is the mechanism that makes region rollout one-click: when a new region's services boot, they register themselves against that region's namespace, and every peer that needs to resolve them can, immediately, with zero manual wiring. Skip the .cost-strip here too — like Config Service, this is a near-free managed service at this traffic level, and a short paragraph saying so is more honest than padding in stat tiles that would all read "negligible."

07

Decisions worth writing down

Decision — Cloud Map over self-hosted Eureka/Consul

No stateful HA cluster to operate per region

AWS Cloud Map beats a self-hosted Eureka or Consul cluster because it avoids running and patching a stateful, highly-available registry per region just to duplicate what ECS already speaks to natively. See ADR-002.

Decision — no hardcoded endpoints anywhere

Every peer address is resolved via Cloud Map DNS, never configured by hand

This is the actual mechanism, not just a principle, behind zero-manual-wiring region rollout: every service resolves its peers' addresses through Cloud Map DNS names at call time. A new region's services need no endpoint list handed to them — they resolve what exists in their own namespace, and stop resolving instances the moment those instances stop passing health checks.
