Search Service — build-time vs. deployment-time infrastructure

Where OpenSearch gets built, what Terraform provisions once versus per-deploy, and the AWS wiring that keeps the index disposable and the query path cheap.

01

Why this needs a build/deploy split at all

Search Service (§2 of the HLD) owns no source data — it's a query layer over an OpenSearch index rebuilt from ProductChanged events. That single fact drives every infra decision below: the index schema and mapping is a build-time artifact (it changes when the code that shapes documents changes), while the index's data is a runtime artifact that gets rebuilt continuously and can be thrown away without data loss — the source of truth is Product Management's DB, not the index.

Treat those as two different lifecycles from day one: build-time work happens once per code change, in CI, before anything touches AWS; deployment-time work happens once per release (or once per region), and it provisions or updates infrastructure that then runs continuously and rebuilds its own contents from events.

02

Build-time: what CI produces

Nothing in this phase touches a live OpenSearch domain. It produces artifacts that deployment-time consumes.

Build Query-layer image

on every merge to main
  • Compile the stateless query service (the thing that translates gateway requests into OpenSearch DSL) into one container image.
  • Tag with commit SHA, push to ECR — same repo pattern already used for the Spring Boot services.
  • No environment- or region-specific values baked in — those come from AppConfig at boot (§5 of the HLD).

Build Index template & mapping

versioned alongside the consumer code
  • The event consumer (Lambda or a small Fargate task) that turns ProductChanged into index documents owns a versioned mapping file — analyzers, field types, shard count.
  • A mapping change ships as a new index version (products-v13), never a mutation of the live index — OpenSearch mappings aren't safely mutable in place for field-type changes.
  • CI validates the mapping against a sample document set before it's allowed to merge.
Why version the index name, not the domain: reindexing safely means writing to products-v13 while products-v12 still serves traffic, then flipping an alias — a build-time contract (the mapping) determines a deploy-time action (alias swap) with zero downtime.
EventBridge vs. Kafka for this edge, specifically: the backfill in §03 works by replaying ProductChanged events into the new index version — which only produces a correct index if every event for a given product arrives in the order it was published. EventBridge doesn't guarantee that. Today's volume makes this a latent risk rather than an active bug, but it's the one edge in the whole system flagged as a Kafka (MSK) candidate — see ADR-009 for the exact triggers and why this edge, and only this edge, is being watched rather than switched preemptively.

Deployment-time: what gets provisioned and reconciled

This is where Terraform and the OpenSearch domain itself live. Split further into provision-once-per-region infrastructure and reconcile-every-release application state.

Deliberate boundary: Terraform provisions the OpenSearch domain (compute, storage, network, access policy) — it does not create indices, mappings, or aliases inside that domain. Index lifecycle is an application concern run by a bootstrap job, because index creation depends on the mapping version shipping in that release, not on infrastructure state. Mixing the two makes every mapping change require a Terraform apply, which is the wrong tool for something that should ship at the same cadence as application code.

04

Terraform module layout

One module, called once per region, matching the HLD's §6 pattern for the other ten services — region is a variable, not a fork.

modules/search-service/main.tf 
// domain: infra only — no index/mapping resources live here
resource "aws_opensearch_domain" "search" {
  domain_name    = "search-${var.region_short}-${var.environment}"
  engine_version = "OpenSearch_2.15"

  cluster_config {
    instance_type          = var.node_instance_type
    instance_count         = var.node_count
    zone_awareness_enabled = true
    zone_awareness_config { availability_zone_count = 3 }
  }

  ebs_options {
    ebs_enabled = true
    volume_type = "gp3"
    volume_size = var.volume_size_gb
  }

  vpc_options {
    subnet_ids         = var.private_subnet_ids
    security_group_ids = [aws_security_group.search_sg.id]
  }

  encrypt_at_rest      { enabled = true }
  node_to_node_encryption { enabled = true }

  // discovery: register the domain endpoint, not an instance —
  // the query-layer resolves this via Cloud Map, never a hardcoded URL
}

resource "aws_service_discovery_service" "search_query_layer" {
  name = "search"
  dns_config {
    namespace_id = var.cloudmap_namespace_id
    dns_records { type = "A" ttl = 10 }
  }
}

module "search_ecs_service" {
  source          = "../ecs-fargate-service"
  service_name    = "search-query-layer"
  image           = "${var.ecr_repo_url}:${var.image_tag}"
  desired_count   = var.query_layer_task_count
  cpu             = 512
  memory          = 1024
  autoscale_on    = "request_count" // query volume, not CPU — see HLD §2
}
envs/ap-southeast-1/search.tfvars 
region_short          = "apse1"
node_instance_type    = "or2.medium.search"
node_count             = 3
volume_size_gb         = 50
query_layer_task_count = 2

Region rollout is one command, matching §6 of the HLD: terraform apply -var-file=envs/ap-southeast-1/search.tfvars. State is keyed per region (separate backend key), so a bad plan in one region can't touch another's domain.

05

AWS service choices, and why

LayerChoiceAlternative consideredWhy this one
Index store managed Amazon OpenSearch Service Self-hosted OpenSearch on EC2/ECS Managed snapshots, patching, and zone-aware replica placement remove exactly the operational surface a search cluster otherwise demands — the HLD's own §7 default.
Query compute managed ECS Fargate, stateless Lambda per query Query latency needs a warm connection pool to OpenSearch; Lambda cold starts would show up directly in search-result latency. Fargate autoscales on request count per HLD §2.
Index-build consumer managed AWS Lambda, triggered by EventBridge rule on ProductChanged A standing Fargate consumer Indexing is bursty and idle between catalog changes — same reasoning the HLD applies to Notification Service. Pay-per-invocation beats a standing task for an event volume this irregular.
Reindex/backfill job self-run one-shot ECS task, run by CI on deploy Terraform provisioner (local-exec) Reindexing is an application action with retries and progress tracking — embedding it in Terraform couples infra state to a long-running data job, which is the same anti-pattern the module layout above avoids for index creation.
Alias management self-run bootstrap Lambda invoked post-deploy Manual API call The alias flip (products → products-v13) is the actual zero-downtime cutover; scripting it makes the one-click region story in HLD §6 hold for Search too.
06

What a new region actually costs to spin up

Per the HLD's one-click multi-region goal (§6), adding a region for Search means these three provisions run under the same ./deploy.sh --region call — nothing Search-specific breaks the pattern.

Domain floor
3 nodes
zone-aware across 3 AZs — the minimum for a production OpenSearch domain, not a cost optimization to skip
Cold-start cost
~0
index is empty until the backfill job runs — no data migration between regions, just replay events
Query layer
2 tasks
scales on request volume post-launch; starts at the floor Fargate needs for HA

Because the index rebuilds from events rather than replicating data, a new region's Search stack needs no cross-region data transfer step at all — it needs the EventBridge bus reachable (or a regional bus with forwarded rules) and enough backfill time to catch up, which is minutes, not a migration project.

07

Decisions worth writing down

Decision — index lifecycle is not a Terraform resource

Terraform owns the domain, application code owns the index

Creating indices, applying mappings, and flipping aliases happen through a bootstrap job run as part of deployment, not through aws_opensearch_domain resources or provisioners. This keeps a mapping change on the same release cadence as the code that produces documents, and keeps terraform plan free of noise from index churn.

Decision — versioned index names, aliased in production

products-vN + alias, never a mutated live index

A breaking mapping change ships as a new index version built alongside the old one, backfilled from the event stream, then cut over via alias swap. The query layer only ever queries the alias, never a version number directly — this is what makes the OpenSearch mapping a build-time artifact instead of a runtime coupling.

Decision — consumer is Lambda, query layer is Fargate

Split compute by traffic shape, not by convenience

The indexing consumer is bursty and tolerant of a few hundred milliseconds of cold start; the query layer is latency-sensitive and benefits from a warm connection pool. Running both on the same compute type would force a compromise neither side needs — matches the HLD's per-service reasoning in §7 rather than defaulting everything to Fargate for consistency's sake.
