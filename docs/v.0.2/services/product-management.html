Product Management — the catalog of record and the cost of splitting it out

Product Management owns the largest slice of the monolith's data by a wide margin. This document lays out what it owns today, how it's read by nearly every write path elsewhere in the system, and why extracting it is the single biggest cross-cutting migration risk in the whole decomposition.

01

Overview

Product Management is the catalog of record for every sellable item on the marketplace — Drug, Consumable, Non-consumable, Supplement, Cosmetic, and Food/Infant categories, plus the shared lookup masters (molecules, dosage forms, categories, GST rates, pack types) that all of them reference.

The traffic shape is lopsided in a way that matters for every decision below: reads dominate by a huge margin — every product listing, every quote, every order confirmation touches this data — while writes are comparatively rare and low-throughput, because catalog changes (a new SKU, a price revision, a stock update) happen at the pace of a seller's back office, not at the pace of buyer traffic. That asymmetry is why this service scales reads aggressively (replicas, caching) while writes stay on a single, unremarkable path. It is also, by table count, the single largest domain in the entire system — see §02.

02

Data ownership

A full entity audit of the current monolith counted ~62 entities/tables under entity/product/** — roughly 59% of the system's ~106 tables. No other domain comes close; this is the catalog, and cataloging six distinct product verticals plus their shared lookups is inherently table-heavy.

The self-contained part is easy; the referenced-from-outside part isn't: all 62 tables above are internally cohesive — they FK to each other and to nothing outside entity/product/**, which means splitting Product into its own database is, on Product's own terms, straightforward. The problem is that every other domain holds foreign keys into Product: Quotation's tbl_quote_request and Order's tbl_order_item both carry a product_id that today resolves with a plain SQL join inside one database. The moment Product moves to its own database, that join is gone — those services must be rewritten to hold an opaque product-ID reference and resolve product data via a sync API call instead of a foreign key. This is a schema change in every consuming service, not just an infrastructure change in Product.
03

Communication

Product Management is called synchronously, in-request, by the two services with the sharpest latency budgets in the system — and it emits one asynchronous event stream outward.

Sync IN Order & Quotation Management

buyer is waiting in the same request
  • Order Management calls in for price and stock confirmation before an order is placed — the buyer's checkout request blocks on this call.
  • Quotation Management calls in for pricing when generating a quote — same shape, different trigger.
  • Both are load-bearing, latency-sensitive reads hit on nearly every write path elsewhere in the system. The right mitigation lives on the caller's side: cache Product responses aggressively in Order and Quotation rather than treating every checkout as a fresh round trip.

Async OUT Search Service

on every catalog change
  • Product emits ProductChanged events (or a CDC stream off its own tables) whenever catalog data changes.
  • Search Service rebuilds its OpenSearch index from this stream — eventually consistent by design, per ADR-005.
  • The relationship is strictly one-directional: Search never calls back into Product on the read path. A search query is served entirely from the index; Product is not in that call chain at all.
  • This is the one edge in the system flagged as a Kafka (MSK) candidate rather than staying on EventBridge long-term — ordered, replayable delivery matters here because Search's index-backfill process replays this exact stream. See ADR-009 for the specific triggers and why every other async edge stays on EventBridge.

05

Deployment

ECS Fargate, autoscaled specifically on read volume — not CPU. Given the read-heavy traffic shape from §01, CPU utilization is a lagging, noisy proxy for the thing that actually predicts load here (concurrent browse/lookup requests); scaling directly on request count keeps capacity aligned with the metric that's actually driving it.

Storage is Aurora PostgreSQL with a Global Database for multi-region reads, fronted by ElastiCache Redis to absorb browse traffic without hitting the writer directly. Redis is there specifically because catalog reads are so much more frequent than catalog writes that caching the hot path is a much bigger win here than it would be for a service with a flatter read/write ratio.

modules/product-management/main.tf 
// one global cluster, one primary write region — see §06 for the read topology
resource "aws_rds_global_cluster" "product" {
  global_cluster_identifier = "product-global"
  engine                    = "aurora-postgresql"
  engine_version            = "15.4"
  database_name             = "product"
}

// regional Aurora cluster — primary in the write region, secondary elsewhere
resource "aws_rds_cluster" "product_regional" {
  cluster_identifier        = "product-${var.region_short}"
  engine                    = "aurora-postgresql"
  engine_version            = "15.4"
  global_cluster_identifier = aws_rds_global_cluster.product.id
  db_subnet_group_name      = var.db_subnet_group
  vpc_security_group_ids    = [aws_security_group.product_db_sg.id]
  is_primary_cluster        = var.is_write_region
}

// Redis in front of the writer — absorbs browse traffic, not a write cache
resource "aws_elasticache_replication_group" "product_cache" {
  replication_group_id = "product-cache-${var.region_short}"
  description           = "catalog read cache"
  node_type             = var.cache_node_type
  num_cache_clusters    = var.cache_node_count
  engine                = "redis"
  automatic_failover_enabled = true
}

module "product_ecs_service" {
  source        = "../ecs-fargate-service"
  service_name  = "product-management"
  image         = "${var.ecr_repo_url}:${var.image_tag}"
  desired_count = var.task_count
  cpu           = 1024
  memory        = 2048
  autoscale_on  = "request_count" // read volume, not CPU
}
06

Scaling & region topology

Product Management runs active-active for reads via Aurora Global Database, per ADR-007. It's one of the services the HLD explicitly names as tolerant of read-replication lag — a buyer browsing a slightly stale catalog for a few hundred milliseconds is a non-event, unlike Order, Billing, Seller, or Buyer, which all stay single-writer, single-region-authoritative because staleness there means money or state moving incorrectly.

Writes still funnel through one primary region — catalog changes from a seller are not so frequent or latency-sensitive that they need multi-writer complexity. Reads fan out globally through the secondary Aurora clusters plus per-region ElastiCache, so a buyer in any region gets local read latency without Product ever needing multi-region write conflict resolution.

07

Decisions worth writing down

Decision — Product's own split is easy; the cross-service FK migration is not

The 62 tables split cleanly; every product_id foreign key elsewhere does not

Product Management's own schema is self-contained and splits into its own database with no internal friction. But Quotation's tbl_quote_request, Order's tbl_order_item, and a presumably-future cart all hold real foreign keys into Product tables today. Extraction forces every one of those services to replace a database-level join with an opaque product-ID reference resolved through a sync API call. This is, by a wide margin, the biggest cross-cutting migration risk anywhere in the decomposition — bigger than any single service's internal rework, because it touches the internals of every consuming service at once, not just Product's.

Decision — ElastiCache in front of Aurora, specifically for this service

Why Product gets a cache layer that Order doesn't

Product's read/write ratio is extreme: browse and lookup traffic vastly outnumbers catalog writes, and that traffic is exactly the kind a cache absorbs well (same SKUs, read repeatedly, invalidated infrequently). Order Management doesn't get this treatment because its reads are mostly one-off, per-order lookups rather than repeated browse traffic — caching there would add invalidation complexity without meaningfully reducing writer load. The decision to cache is driven by traffic shape, not a blanket "cache everything" policy.
