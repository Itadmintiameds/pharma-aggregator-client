API Gateway — the platform's sole client entry point

Why every client request, and only client requests, pass through one component — routing, authN/authZ, and rate limiting live here so no domain service has to reimplement them or be reachable from the internet directly.

01

Overview

API Gateway is the platform edge: routing, authN/authZ enforcement, and rate limiting all live here, in front of every domain service. Every client request — browser or mobile, read or write — passes through it before it reaches Seller User, Buyer User, Order Management, Quotation Management, Product Management, Search, or Billing.

That single fact fixes its scaling shape: the Gateway scales 1:1 with total client traffic across the whole platform, not with the load of any one domain service. A spike in Order Management's request volume is a Gateway concern exactly as much as a spike in Search's, because both arrive through the same front door. The corollary is the security posture it buys: no domain service is directly reachable from the internet. Every one of them sits behind the Gateway, on a private network path, and the Gateway is the only thing with a public listener.

02

Data ownership

None. API Gateway holds no persistent business data and no config store of its own.

Routing rules and auth policy are configuration it reads — sourced from Config Service and the identity provider (Cognito/JWT issuer) — not state it owns or is a system of record for. There's no table to list here, and forcing one would misrepresent what this service is: a stateless routing and policy-enforcement layer, not a data owner. This is the structural difference between a platform service and a domain service — the "data ownership" section is real for Order Management or Product Management; for the Gateway it's a deliberate blank.

03

Communication

Sync IN — from every client (browser, mobile app) for all reads and writes across the platform. This is synchronous by nature: the UI is sitting there waiting on a response, there's no async variant of "load the seller dashboard" or "submit a quotation."

Sync OUT — to whichever domain service the matched route maps to. The Gateway itself does no business logic; it terminates TLS, validates the JWT, checks rate limits, and forwards.

Explicitly out of scope: service-to-service calls. When Order Management calls Product Management to confirm price/stock, or Quotation Management calls Order Management to create an order on accept, those calls bypass the Gateway entirely and resolve directly via Cloud Map / Discovery Service (see discovery-service.html). The Gateway is client-facing only — it is not an internal service mesh, and routing internal traffic through it would double its load for no security benefit, since internal traffic is already inside the private network the Gateway exists to protect the boundary of.

Client traffic fans in from the left, terminates at the Gateway, and fans out (sync) to whichever domain service owns the route. Domain services are grouped into one box for legibility — the Gateway's fan-out is identical in shape to all seven, so drawing seven boxes would add clutter, not information.

What the diagram deliberately leaves out: any edge between domain service boxes. Those calls exist (Order→Product, Quotation→Order) but they resolve peer-to-peer via Discovery Service, never back through this box — see discovery-service.html for that path.

05

Deployment

Amazon API Gateway (managed) is the primary choice. It handles routing, request/response transformation for the common cases, throttling, and a Cognito/JWT authorizer with no cluster to run or patch. This is the managed-first default: reach for the self-hosted alternative only when a concrete need outgrows it, not preemptively.

Fallback: self-hosted Spring Cloud Gateway on ECS Fargate — kept as an explicit escape hatch for the day routing or request-transformation requirements exceed what the managed service exposes (custom filter chains, non-standard protocol translation, request bodies too large or too irregular for AppGW's transformation templates). Standing it up before that day arrives would mean operating a cluster, patching it, and scaling it — all to duplicate a decision AWS has already made well.

modules/api-gateway/main.tf 
// managed HTTP API — routes fan out to domain services over private integrations
resource "aws_apigatewayv2_api" "platform" {
  name          = "platform-${var.region_short}-${var.environment}"
  protocol_type = "HTTP"
}

resource "aws_apigatewayv2_authorizer" "jwt" {
  api_id           = aws_apigatewayv2_api.platform.id
  authorizer_type  = "JWT"
  identity_sources = ["$request.header.Authorization"]
  jwt_configuration {
    audience = [var.cognito_app_client_id]
    issuer   = "https://cognito-idp.${var.aws_region}.amazonaws.com/${var.cognito_user_pool_id}"
  }
}

resource "aws_apigatewayv2_integration" "order_mgmt" {
  api_id             = aws_apigatewayv2_api.platform.id
  integration_type   = "HTTP_PROXY"
  integration_uri    = var.order_mgmt_cloudmap_arn
  integration_method = "ANY"
  connection_type    = "VPC_LINK"
  connection_id      = aws_apigatewayv2_vpc_link.private.id
}

resource "aws_apigatewayv2_route" "orders" {
  api_id             = aws_apigatewayv2_api.platform.id
  route_key          = "ANY /orders/{proxy+}"
  target             = "integrations/${aws_apigatewayv2_integration.order_mgmt.id}"
  authorization_type = "JWT"
  authorizer_id      = aws_apigatewayv2_authorizer.jwt.id
}

resource "aws_apigatewayv2_stage" "live" {
  api_id      = aws_apigatewayv2_api.platform.id
  name        = var.environment
  auto_deploy = true

  default_route_settings {
    throttling_burst_limit = var.throttle_burst
    throttling_rate_limit  = var.throttle_rate
  }
}

One route block per domain service, all sharing the same authorizer and VPC Link into the private network the domain services live on — nothing behind the Gateway needs a public IP.

06

Scaling & region topology

With managed API Gateway, scaling is automatic — effectively unlimited horizontal scale within account service limits, no capacity planning on this side. The interesting question isn't "does it scale," it's topology: one global gateway with regional backends, or one gateway per region?

Recommendation: one gateway per region, with Route 53 latency-based routing in front directing each client to its nearest regional gateway. This matches the platform's one-click-per-region rollout goal in ADR-006 — standing up a new region means deploying a new, independent gateway from the same Terraform module, not editing a shared global resource that every other region also depends on. A single global gateway would turn "add a region" into "carefully modify a resource in production that every existing region's traffic also flows through" — exactly the kind of shared-blast-radius change the per-region pattern elsewhere in the platform is built to avoid.

07

Decisions worth writing down

Decision — all client traffic through the Gateway, zero direct exposure

No domain service is directly reachable from the internet

Every client request, without exception, enters through API Gateway. Domain services live entirely on the private network and are only reachable via the Gateway's VPC Link integrations — see ADR-008. This centralizes authN/authZ enforcement and rate limiting in one place instead of asking eleven services to each implement (and each potentially get wrong) the same concerns.

Decision — managed by default, self-hosted only on concrete need

Amazon API Gateway first; Spring Cloud Gateway on Fargate is an escape hatch, not a plan

The managed service is the default for every environment and region. Self-hosted Spring Cloud Gateway stays on the shelf until a specific routing or transformation requirement is identified that the managed offering can't express — it is not built preemptively "in case we need it," because that would mean carrying cluster-operations cost for a capability nothing currently uses.
