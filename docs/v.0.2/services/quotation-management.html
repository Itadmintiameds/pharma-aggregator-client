Quotation Management — negotiation state and the single-table problem

Why one table backing two flows and three cross-domain foreign keys is a bigger problem than it looks, and how the negotiation trail should actually be modeled once this becomes its own service.

01

Overview

Quotation Management owns buyer quote requests, seller quote responses, and the negotiation state that sits between them — the pre-sale conversation that either dies quietly or converts into an Order.

Traffic here is bursty in a way that tracks B2B negotiation cycles rather than steady retail browsing: quiet stretches interrupted by clusters of activity when a buyer organization is actively sourcing, a seller is responding to a batch of RFQs, or a negotiation round is closing out before a purchasing deadline. That shape matters for how this service should scale — see §6.

02

Data ownership

The entity audit shows exactly one table in entity/quote today: tbl_quote_request. There is no separate seller-response table and no separate negotiation-state table — everything lives as status fields on this single row.

That one table backs both quoting flows in the product: "Request Price Option" (a buyer asking a seller for a price on a specific product) and RFQ "Get a Quote" (a more open-ended sourcing request), discriminated by a requestType enum column rather than by separate tables or separate services.

Open architecture question, answered as a decision: does the target Quotation Management service need a dedicated response/negotiation-history table, or does the single-row-with-status-transitions model carry forward as-is? A single mutable row that gets overwritten on every back-and-forth loses the negotiation trail — there's no record of what the buyer's counter-offer was, what the seller's first response said, or how many rounds it took to close. The recommendation, treated as a decision in §7, is a companion tbl_quote_negotiation_history table that appends one row per exchange rather than mutating the parent request.

Second flag — three-way cross-domain foreign keys: today's QuoteRequest entity directly foreign-keys BuyerUser, Seller, and ProductDetails in the same row. That's fine in a monolith with one shared database; it breaks the moment Buyer, Seller, and Product become separate service databases, because a foreign key can't reach across a database boundary. The target service has to store these as opaque IDs and resolve them via API calls at read time — never as FKs. This is a direct consequence of the service-boundary split (see §7).

03

Communication

Quotation makes two outbound synchronous calls and receives none — it has no async edges in the source HLD.

Sync OUT Quotation → Product Management

pricing lookup during quote generation
  • Generating a quote requires current pricing from Product Management in the same request — the buyer needs to see an actual number, not a stale one from whenever the product was last indexed.

Sync OUT Quotation → Order Management

create-order-on-accept
  • When a buyer accepts a quote, Quotation calls Order to create the order before returning "accepted" — the order must exist before the acceptance response goes back to the buyer.
  • This is the one place quotation data crosses into Order, and it crosses as a create call carrying a reference, never as a shared table or a copy of the quote row.

05

Deployment

ECS Fargate, Aurora PostgreSQL — moderate volume, transactional, same engine as Order since a quote acceptance hands off to Order synchronously and both need to reason about consistency the same way.

modules/quotation-management/main.tf 
// same single-writer-plus-standby shape as Order — see ADR-007
resource "aws_rds_cluster" "quote_db" {
  cluster_identifier      = "quotation-mgmt-${var.environment}"
  engine                  = "aurora-postgresql"
  engine_version          = "15.4"
  master_username         = var.db_master_username
  master_password         = var.db_master_password
  backup_retention_period = 7
}

resource "aws_rds_cluster_instance" "quote_db_writer" {
  cluster_identifier = aws_rds_cluster.quote_db.id
  instance_class     = var.db_instance_class
  engine             = aws_rds_cluster.quote_db.engine
}

module "quotation_ecs_service" {
  source        = "../ecs-fargate-service"
  service_name  = "quotation-management"
  image         = "${var.ecr_repo_url}:${var.image_tag}"
  desired_count = var.task_count
  cpu           = 512
  memory        = 1024
  autoscale_on  = "request_count" // bursty around negotiation cycles, not steady load
}
06

Scaling & region topology

Quotation runs single-writer with a warm standby, the same bucket as Order Management, per ADR-007.

It lands in that bucket for the same reason as Order: it's transactional state that feeds directly into a synchronous order-creation call, and an active-active write topology would introduce the same conflict-resolution problem for negotiation state that it would for order state — which counter-offer is the current one if two regions accept writes independently. Autoscaling on request count handles the bursty traffic shape without changing the write topology.

07

Decisions worth writing down

Decision — add a negotiation-history companion table

tbl_quote_negotiation_history instead of overloading one mutable row

The current model stores negotiation state as status fields on tbl_quote_request, which means every round of back-and-forth overwrites the last one — there's no record of the buyer's original ask, the seller's counter, or how the price moved between them. A companion history table that appends one row per exchange fixes this without changing what the parent request row means: the request stays the current state, the history table becomes the audit trail. This is worth doing before Quotation splits into its own service, not after, because retrofitting history onto live negotiation data is much harder than starting with it.

Decision — opaque IDs instead of foreign keys across service boundaries

Buyer, Seller, and Product references become resolved-via-API, not FKs

Today's QuoteRequest foreign-keys BuyerUser, Seller, and ProductDetails directly because they all live in one database. Once Buyer, Seller, and Product become separate service databases under the service-boundary split, those foreign keys have nothing to point at — the target Quotation Management service stores each as an opaque ID and resolves it via a synchronous API call when it needs the actual buyer, seller, or product data. This is a direct, mechanical consequence of the boundary split, not a separate design choice.
