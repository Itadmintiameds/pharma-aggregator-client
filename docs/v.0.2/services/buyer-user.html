Buyer User Service — schema, deployment, and auth-pattern alignment

What Buyer User owns today, how it mirrors Seller User's shape at lower volume, and the auth-table inconsistency between the two domains that needs a single answer before either ships as a service.

01

Overview

Buyer User owns the buyer's identity: profile, registration, onboarding documents, and buyer auth. It's the same shape as Seller User — a registration/approval flow feeding a live profile record, with the same document-upload and OTP mechanics — just lighter in volume, since buyer onboarding doesn't carry the GST/bank-details/coordinator surface that seller onboarding does.

Because the shape matches Seller User, most of the reasoning in that doc carries over directly: registration traffic is bursty around onboarding pushes rather than steady, and document upload is I/O bound, not CPU bound, so it scales on request queue depth rather than CPU. The difference here is scale, not architecture — Buyer User should be sized down from Seller User's numbers (fewer tasks, smaller instance class), not redesigned.

Inconsistency worth naming: Buyer already has its own dedicated OTP/refresh-token tables (tbl_buyer_signup_otp, tbl_buyer_login_otp, tbl_buyer_refresh_tokens), fully scoped to this domain. Seller, by contrast, reuses a generic shared entity/auth package (tbl_user, tbl_signup_otp, tbl_refresh_tokens, tbl_login_otp) also used by seller-coordinator login. The two domains solved the same problem two different ways. This doc and the Seller User doc both flag it — the recommendation (see Decisions) is for Seller to adopt Buyer's pattern, not the reverse, since Buyer's is already proven and per-domain auth avoids a cross-service dependency once both are split out.

Buyer User FKs into the same shared master tables as Seller User — tbl_state_master, tbl_district_master, tbl_taluka_master, tbl_buyer_type_master, tbl_document_type_master. These remain a shared read-only reference module, not owned by either service, and get cached at the edge.

03

Communication

Same shape as Seller User: Buyer User is mostly called, rarely calls out, and the inbound calls are read-only eligibility/profile lookups that should be cached rather than hit live on every request.

Sync Inbound eligibility/profile lookups

on order and quotation write paths
  • Order Management → Buyer User: is this buyer account active before accepting an order.
  • Quotation Management → Buyer User: buyer-profile/eligibility check before a quotation can be issued to them.
  • Lower call volume than Seller User's equivalent (fewer buyer-side gating checks than seller-side ones today), but the same caching discipline applies — short-TTL cache, invalidated on status change.

Platform Boot-time platform calls

on service startup, not business traffic
  • Registers with Discovery Service so callers can resolve it without hardcoded endpoints.
  • Pulls config from Config Service at boot — DB connection, S3 bucket, feature flags.

05

Deployment

Same module shape as Seller User — ECS Fargate, Aurora PostgreSQL, S3 for documents via the existing S3Service pattern — sized down rather than redesigned. Lower desired_count and a smaller DB instance class reflect the lighter volume noted in §01; the resource graph and autoscaling metric (request queue depth, not CPU) are unchanged from Seller User.

06

Scaling & region topology

Buyer User is in the same single-writer with warm standby bucket as Seller User, for the same reason: correctness over read scale.

Buyer registration and login are transactional and identity-bearing in exactly the way seller registration is — two regions independently writing buyer accounts or issuing refresh tokens against divergent data is a reconciliation problem, not something that resolves itself the way a stale product listing does. There's no argument for treating Buyer differently from Seller here just because its volume is lower; volume affects sizing, not the write-consistency requirement.

Failover follows the same pattern as Seller User: a warm standby replica, promoted via a controlled runbook rather than an automatic instant cutover, with Route 53 repointed once the promoted cluster is confirmed healthy.

Writer region floor
1 task
lower than Seller User's 2-task floor, reflecting lighter steady-state volume
Standby region floor
1 task + replica

07

Decisions worth writing down

Decision — collapse Temp/Live into one schema, same as Seller

Buyer's two-stage lifecycle gets one identity with a status column

Buyer's split is simpler than Seller's (two stages, not three — there's no separate "pending admin approval" table family the way Seller has tbl_pending_seller), but the same principle applies: tbl_temp_buyer and tbl_buyer should become one entity with a lifecycle_status column rather than two tables with independent keys, using tbl_temp_buyer_review_history's existing history pattern to preserve the audit trail. This keeps Buyer User's schema simpler than Seller's by construction, not by accident — there's no reason to introduce a third stage Buyer doesn't currently have.

Decision — Buyer's per-domain auth pattern is the one to standardize on

Keep Buyer's dedicated OTP/refresh-token tables; Seller adopts this pattern, not the reverse

Buyer already owns tbl_buyer_signup_otp, tbl_buyer_login_otp, and tbl_buyer_refresh_tokens scoped entirely to its own domain — no changes needed here. The call to make (recorded in full in the Seller User doc) is that Seller migrates off the shared entity/auth package onto this same pattern, because a shared auth schema becomes a cross-service coupling the moment Seller and Buyer split into separate services, and Buyer's version is already running in production. Buyer User Service ships its auth tables as-is; it isn't the side that has migration work to do.

Decision — no IFSC or terms-master ownership on the Buyer side

tbl_ifsc_overrides stays with Seller; tbl_terms_master goes to shared legal content

tbl_ifsc_overrides validates bank details, which Buyer registration doesn't collect — it has no reason to touch Buyer User's schema and stays fully on the Seller side (see Seller User doc). tbl_terms_master, despite sitting under entity/temp/seller today, is legal content Buyer will also need at registration — it shouldn't be duplicated into Buyer's schema either. Both Buyer User and Seller User should read it from a shared legal-content table in the reference module, not own a copy each.
