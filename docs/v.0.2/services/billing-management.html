Billing Management — extracting invoicing without duplicating Order's data

Why Billing is a migration target rather than a greenfield service, why its database has to be physically separate from Order's, and how it renders invoices without ever storing a second copy of an order's line items.

Status: Draft Owns: Billing Management (§5 of HLD) Last updated: 2026-09-02 ← back to service index

01

Overview

Billing Management owns invoices, payment records, and ledger entries. It references orders by order_id and stores no copy of any order's line items — line-item detail is fetched from Order Management at the moment an invoice is rendered, never persisted a second time.

Traffic here is spiky rather than steady: it consumes Order events asynchronously as they arrive through normal order volume, but load concentrates hard around reconciliation and month-end close, when finance workflows pull large batches of invoices and payment records at once. Billing's deployment and scaling posture (§5, §6) is built around that spike, not around average daily order volume.

02

Data ownership

Zero dedicated tables exist for Billing today. Payment (tbl_payment) and Invoice (tbl_invoice) currently live inside Order's entity/order package — there is no entity/billing package in the monolith at all.

That makes Billing a migration target, not a greenfield build: standing it up as its own service means extracting two existing tables (with their existing data and existing code paths) out of Order's package, plus adding a ledger_entries table that doesn't exist yet to represent the double-entry-style record of what was invoiced, paid, and refunded. This is explicitly not a simple relabel — a shared schema or a read-only view into Order's tables would technically "work" but would leave the no-duplication rule unenforceable, because nothing would stop a future query from joining across the boundary.

Why the migration has to be physical: the tables must move to Billing's own schema and cluster, separate from Order's, so that no query — not a careless one, not a well-intentioned one — can join Billing data against Order's tables directly. Physical separation is what turns ADR-004's no-duplication rule from a convention into something enforced at the infrastructure level. See the Order Management doc's data-ownership section for the other side of this same migration.
03

Communication

Billing is almost entirely reactive: one async inbound stream from Order, one on-demand sync call back to Order for rendering, and one async outbound stream to Notification.

Async IN Order Management → Billing

OrderCreated / OrderStatusChanged via EventBridge
  • Billing reacts to these events to create and update invoice and payment records.
  • Billing can lag behind Order by seconds without the buyer noticing — order confirmation never waits on Billing having processed anything.

Sync OUT Billing → Order Management

line-item lookup, on demand, at invoice-render time only
  • When an invoice needs to be rendered, Billing asks Order for that order's line items on the spot — "give me line items for order_id X."
  • The result is used to render the invoice and then discarded — never written back into a Billing table. There is no persisted copy, ever.

Async OUT Billing → Notification Service

InvoiceGenerated / PaymentFailed events
  • Payment-status emails are fire-and-forget from Billing's perspective, consistent with the platform-wide rule that Notification never receives a synchronous call.

05

Deployment

ECS Fargate with bursty autoscaling for month-end reconciliation spikes, and Aurora PostgreSQL in a schema and cluster physically separate from Order's — the infra-level guarantee that no query can join across the two.

modules/billing-management/main.tf 
// deliberately its own cluster resource, never a schema inside
// order_db — this is what makes the no-duplication rule (ADR-004)
// enforceable rather than just documented
resource "aws_rds_cluster" "billing_db" {
  cluster_identifier      = "billing-mgmt-${var.environment}"
  engine                  = "aurora-postgresql"
  engine_version          = "15.4"
  master_username         = var.db_master_username
  master_password         = var.db_master_password
  backup_retention_period = 14 // longer retention: finance/reconciliation needs
}

resource "aws_rds_cluster_instance" "billing_db_writer" {
  cluster_identifier = aws_rds_cluster.billing_db.id
  instance_class     = var.db_instance_class
  engine             = aws_rds_cluster.billing_db.engine
}

module "billing_ecs_service" {
  source        = "../ecs-fargate-service"
  service_name  = "billing-management"
  image         = "${var.ecr_repo_url}:${var.image_tag}"
  desired_count = var.task_count_floor
  cpu           = 512
  memory        = 1024
  autoscale_on  = "request_count"
  // burst ceiling sized for month-end reconciliation, not steady state
  max_count     = var.task_count_burst_ceiling
}
06

Scaling & region topology

Single-writer with a warm standby, transactional and write-sensitive per ADR-007, with autoscale burst capacity layered on top for month-end volume.

The write topology decision is the same reasoning as Order and Quotation: payment and invoice records are the kind of data where an active-active conflict-resolution problem is worse than a controlled standby promotion during a regional outage. What's different for Billing is the compute-scaling axis — it needs to burst hard for reconciliation without changing its write topology, which is why the Terraform in §5 sizes a burst ceiling separately from the baseline task count.

07

Decisions worth writing down

Decision — physically separate database, never a shared schema

Billing's Aurora cluster is its own resource, distinct from Order's

A shared schema or a view into Order's tables would satisfy the letter of "Billing doesn't duplicate order data" while leaving the door open for any future code to join across the boundary anyway. Provisioning a genuinely separate cluster makes that impossible at the infrastructure level rather than relying on code review to catch it — this is the direct implementation of ADR-004's no-duplication rule.

Decision — line-item detail is fetched at render time, never persisted

Sync call with a short-TTL cache, not a stored copy

Billing fetches line-item detail from Order Management synchronously, exactly when an invoice is being rendered, and does not write it back into any Billing table. A short-TTL cache is the accepted mitigation for the resulting runtime dependency — it absorbs repeated renders of the same invoice within a short window without reintroducing a persisted copy that could drift from Order's actual state. This trade-off — accept a runtime dependency on Order being reachable, in exchange for zero duplicated data — is the exact reasoning laid out in ADR-004's Consequences section.
