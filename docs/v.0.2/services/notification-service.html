Notification Service — async-only by construction, not convention

The smallest service in the system by data footprint, and the one with the strictest architectural rule: nothing in pharma-aggregator is allowed to call it synchronously, and the deployment shape makes that structurally true rather than just documented.

01

Overview

Notification Service holds no persistent business data — it is, at most, a delivery log. It is fully event-driven end to end: it does nothing until another service emits an event, and it scales to zero in the gaps between bursts.

One rule governs this service above everything else: it must never be called synchronously by another domain service. This isn't a preference or a style guideline — it's a hard architectural constraint, because notification delivery depends on third-party providers (SES, SNS) whose latency and availability are outside pharma-aggregator's control. Letting any other service block on a notification call would mean an SES hiccup could stall an order confirmation or a payment flow. Every design decision in this document follows from keeping that impossible by construction.

02

Data ownership

The entity audit of the current monolith found zero entities or tables associated with notifications. This service is 100% greenfield — there is no existing schema to migrate, no legacy data to reconcile, and no cutover risk on the data side at all.

Proposal, not existing fact: if a delivery log is added later (for support/audit purposes — "did this SMS actually go out"), the recommended shape is a single append-only table, not a normalized schema:

proposed: notification_log 
-- append-only; no updates, no foreign keys into other domains
CREATE TABLE notification_log (
  id          uuid PRIMARY KEY,
  recipient   text        -- email address or phone number, not a user FK,
  channel     text        -- 'email' | 'sms',
  template    text        -- which notification template was used,
  status      text        -- 'sent' | 'failed' | 'retried',
  sent_at     timestamptz
);

Even this proposed table stays append-only and deliberately avoids foreign keys into other domains' user or order tables — it stores enough to answer "was this delivered," not a joinable relationship to the rest of the system. That keeps this service's greenfield status intact even after the log exists.

03

Communication

Every inbound call to this service is asynchronous. There is no synchronous inbound path, by design.

Async IN Order Management

order confirmation
  • Emits an event when an order is placed; Notification picks it up and sends the confirmation email/SMS.
  • Order's own request completes and returns to the buyer without waiting on delivery.

Async IN Billing Management

InvoiceGenerated / PaymentFailed
  • Both events trigger a notification — an invoice email, or a payment-failure alert.
  • Same shape: Billing fires the event and moves on, it never waits for the send.
Why zero sync inbound calls, by design: notification delivery depends on SES/SNS, and that dependency carries its own latency, occasional provider outages, and retry logic. None of that can be allowed to sit on another service's critical path — an order confirmation shouldn't fail, or even slow down, because an email provider is having a bad five minutes. Making every inbound path asynchronous means a Notification-side problem is, by construction, invisible to the rest of the system except as a delayed or retried message.

05

Deployment

AWS Lambda, not Fargate. Notification's load is purely event-driven and spiky — bursts around order/billing activity, idle otherwise — and paying for an always-on Fargate task to sit idle between those bursts isn't justified when Lambda scales to zero for free between invocations.

Email goes through SES, SMS through SNS. Both are invoked from inside the Lambda handler, not exposed as anything callable by another domain service.

modules/notification-service/main.tf 
// event-driven compute: no standing task, no idle cost
resource "aws_lambda_function" "notification_handler" {
  function_name = "notification-handler-${var.region_short}"
  role          = aws_iam_role.notification_lambda.arn
  package_type  = "Image"
  image_uri     = "${var.ecr_repo_url}:${var.image_tag}"
  memory_size   = 512
  timeout       = 30
}

// subscribes to every domain event this service cares about — inbound only
resource "aws_cloudwatch_event_rule" "notification_triggers" {
  name = "notification-triggers-${var.region_short}"
  event_pattern = jsonencode({
    "detail-type" = ["OrderConfirmed", "InvoiceGenerated", "PaymentFailed"]
  })
}

resource "aws_cloudwatch_event_target" "to_lambda" {
  rule = aws_cloudwatch_event_rule.notification_triggers.name
  arn  = aws_lambda_function.notification_handler.arn
}

resource "aws_ses_email_identity" "sender" {
  email = var.notification_from_address
}

resource "aws_sns_topic" "sms_outbound" {
  name = "notification-sms-${var.region_short}"
}
06

Scaling & region topology

The simplest region story in the whole system. There's no persistent writer, so there's nothing to fail over and nothing to replicate. A new region needs only the Lambda function, the EventBridge rule, and the SES/SNS identities re-provisioned — no data migration step exists because there's no data to migrate.

07

Decisions worth writing down

Decision — Lambda over Fargate

Idle cost doesn't pay for itself on a spiky, event-driven workload

Notification traffic is bursty and tied to order/billing activity rather than steady request volume. A standing Fargate task would sit idle most of the time, paying for capacity that isn't being used; Lambda scales to zero between bursts and to whatever concurrency a burst needs, with cost tracking actual invocations instead of provisioned idle time. This mirrors the same reasoning the HLD applies to Search's index-build consumer.

Decision — no REST endpoint exposed to internal callers

"Never synchronous" is enforced structurally, not by convention

Notification Service exposes no internal-facing REST API — only an EventBridge subscription. That means another service cannot accidentally call it synchronously even if a developer wanted to: there is no endpoint to call. The "never synchronous" rule from §01 isn't a code-review checklist item, it's a fact about the deployment topology, which is a stronger guarantee than any amount of documentation.
