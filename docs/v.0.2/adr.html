ADR-001 · Accepted

Service boundaries, v0.2

Adopt 11 services — Seller User, Buyer User, Order Management, Quotation Management, Search Service, Product Management, Billing Management, Notification Service, API Gateway, Config Service, Discovery Service. Master/reference data stays a shared module, not a numbered service.

Context

v0.1 proposed 5 coarse domain services. Stakeholders want finer granularity to scale Order, Quotation, Billing, and Search independently, plus explicit platform services instead of implied infrastructure.

Alternatives considered

Keep v0.1's 5-service split; or split further per product category (rejected — no evidence of independent scaling need per category, and it would fragment a self-contained domain for no operational benefit).

Trade-offs

More services to deploy, monitor, and secure individually, in exchange for independent scaling and clearer team ownership per capability.

Consequences

Requires the platform layer (Gateway/Config/Discovery) to be operational before any domain service split delivers value — sequence platform-first in the migration roadmap.

Governs: Seller User Buyer User Order Management Quotation Management Search Service Product Management Billing Management Notification Service
ADR-002 · Accepted

Discovery & Config: AWS-native over self-hosted

Use AWS Cloud Map for discovery and AWS AppConfig + Systems Manager Parameter Store for config, both provisioned per region via the same Terraform module.

Context

One-click multi-region requires services to find each other and get region-correct config without manual wiring.

Alternatives considered

Netflix Eureka + Spring Cloud Config Server; HashiCorp Consul. Both are natural fits for a Spring Boot team, but each is a stateful cluster to run, patch, and replicate per region.

Reason

The backend already deploys via ECS/ECR — Cloud Map integrates with ECS service discovery natively, with no extra cluster to run per region.

Trade-offs

Ties discovery/config to AWS; acceptable since compute, data, and CI/CD are already AWS-committed.

Governs: Config Service Discovery Service
ADR-003 · Accepted

Sync vs async: default to async

A call is synchronous only when the caller cannot return a correct response without the result in the same request (Order↔Product stock/price check, Quotation↔Order creation on accept). Everything else — Billing, Notification, Search indexing — is event-driven over EventBridge.

Context

Cross-service coupling risk grows with every synchronous call added.

Alternatives considered

Sync everywhere (simpler to reason about, but couples the availability of every service to every caller); async everywhere (adds latency/complexity where a real-time answer is genuinely required).

Trade-offs

Async paths need idempotent consumers and a dead-letter queue per consumer; sync paths need circuit breakers so a slow Product Management doesn't cascade into failed orders.

Governs: Order Management Quotation Management Billing Management Notification Service Product Management
ADR-004 · Accepted

Billing owns no Order data copies

Billing's schema stores order_id as a foreign reference only. It's created from an OrderConfirmed event carrying just order id, buyer id, and total; any line-item detail needed for invoice rendering is fetched synchronously from Order Management at render time, never persisted in Billing.

Context

Explicit requirement: Billing must not duplicate Order Management's data.

Alternatives considered

Full data copy via CDC (rejected — reintroduces the duplication being avoided); a shared database/schema (rejected — violates service data ownership and makes the boundary unenforceable).

Trade-offs

Invoice rendering has a runtime dependency on Order Management being reachable; mitigate with a short-TTL cache on the line-item lookup, not a persisted copy.

Governs: Billing Management Order Management
ADR-005 · Accepted

Search Service owns an index, not source data

Search Service has no source-of-truth tables — it maintains an OpenSearch index rebuilt from ProductChanged events published by Product Management.

Context

Search needs to scale independently of Product Management's write path.

Alternatives considered

Query Product Management's DB directly for search (rejected — couples search query load to the transactional catalog DB); Product Management embeds search itself (rejected — different scaling profile, per ADR-001).

Trade-offs

Search results are eventually consistent with catalog changes — acceptable for browse/search, not used for stock/price truth (Order still calls Product Management directly for that).

Governs: Search Service Product Management
ADR-006 · Accepted

One-click multi-region via parameterized IaC

One Terraform module per service, region passed as a variable, remote state isolated per region; the existing GitHub Actions pipeline gains a region workflow_dispatch input instead of being duplicated per region.

Context

Requirement: adding a region should be a single scripted action, not manual per-service setup.

Alternatives considered

Manually provisioned regions (rejected — doesn't meet the one-click requirement and is error-prone at 11 services); a full orchestration platform like AWS Control Tower/Landing Zone (deferred — justified once region count grows past a handful, not needed for the first additional region).

Trade-offs

Requires discipline that nothing is provisioned by hand outside Terraform — any manual change in one region silently diverges from the module and breaks repeatability.

Governs: API Gateway Config Service Discovery Service — all services, per module
ADR-007 · Accepted

Single-writer regions for Order, Billing, Seller/Buyer User, Quotation; active-active for Product, Search, Master Data

Transactional/write-sensitive services (Order, Billing, Seller/Buyer User, Quotation) run single-writer with a warm standby region. Read-heavy, lag-tolerant services (Product Management, Search's OpenSearch index, Master/Reference Data on DynamoDB Global Tables) run active-active across regions.

Context

Aurora PostgreSQL Global Database supports one writer region at a time; true multi-writer needs a different data model entirely.

Alternatives considered

Force everything active-active via DynamoDB (rejected — Order/Billing need relational transactions and strong consistency a key-value multi-writer store doesn't give for free); force everything single-writer (rejected — throws away the real multi-region win for the read-heavy services).

Trade-offs

A regional outage in the primary write region means a controlled Aurora promotion (seconds-to-minutes RTO) for Order/Billing, not instant failover — accepted in exchange for payment/order correctness.

Governs: Order Management Billing Management Seller User Buyer User Quotation Management Product Management Search Service
ADR-008 · Accepted

API Gateway is the only client-facing entry point

Amazon API Gateway fronts all client traffic; no domain service is directly reachable from the internet. Service-to-service calls (Order→Product, Quotation→Order) go direct via Cloud Map resolution, bypassing the gateway.

Context

11 independently deployable services need one consistent place to enforce auth, rate limiting, and routing rather than each reimplementing it.

Alternatives considered

Self-hosted Spring Cloud Gateway on Fargate — kept as a fallback option if routing needs (e.g. complex request transformation) outgrow what managed API Gateway supports.

Trade-offs

API Gateway becomes a single dependency for all client traffic — mitigated by AWS's own multi-AZ SLA, and by keeping service-to-service calls off this path entirely so an internal domain issue doesn't compound with a gateway issue.

Governs: API Gateway Discovery Service
ADR-009 · Accepted

Event backbone: EventBridge by default, Kafka only where replay/ordering/volume demand it

Every async edge in the communication matrix (ADR-003) runs on Amazon EventBridge, with SQS behind each consumer for retry/DLQ handling, unless a specific edge needs one of the properties EventBridge doesn't provide — in which case that ONE edge moves to Amazon MSK (managed Kafka), not the whole system.

Context

EventBridge and SQS cover fan-out and task-queue semantics with no cluster to run, matching ADR-002's AWS-native bias. But EventBridge does not guarantee per-key ordering, its Archive/Replay path is a slow, ops-triggered recovery tool rather than a routine replay mechanism, and its per-event pricing/throughput has a practical ceiling. A generic "use a message broker" instruction leaves every team re-deriving when that ceiling is actually hit.

Decision — the four triggers

An async edge graduates from EventBridge to Kafka (MSK) only when it needs at least one of:

  1. Ordered replay is a correctness requirement — out-of-order delivery silently corrupts state (not just delays it).
  2. Routine replay-from-any-offset is part of normal operation, not disaster recovery — e.g. rebuilding a derived store from scratch.
  3. Multiple independent consumer groups need to read the same stream at their own pace with their own offsets, without N hand-wired EventBridge targets.
  4. Sustained volume exceeds EventBridge's cost/throughput curve — measured, not assumed.
Where this applies today

The Product Management → Search Service edge (ProductChanged) is the only edge in the current service catalog that plausibly hits triggers 1 and 2: Search's index-version cutover (see Search Service §02) replays this stream to backfill a new index version, and an out-of-order update to the same product silently produces a wrong search result with no error. This edge is flagged as a Kafka candidate, evaluated once real event volume is measured — not switched preemptively.

Alternatives considered

RabbitMQ (self-hosted or Amazon MQ) for AMQP-style routing — rejected for now: nothing in the current service catalog needs exchange/topic routing beyond what SQS already does, and it would add a cluster to operate per ADR-002's own reasoning against self-hosted infrastructure. Kafka everywhere by default — rejected as premature: most async edges (Order→Billing, Order→Notification, Billing→Notification) are simple fan-out with no ordering or replay requirement, and running MSK for those adds operational cost with no corresponding benefit.

Trade-offs

A mixed backbone (EventBridge for most edges, Kafka for a specific edge) means two operational models to run instead of one — accepted because forcing every edge onto whichever technology the hardest edge needs is the more expensive mistake in the other direction. Revisit per-edge, not system-wide, as real traffic data comes in.
