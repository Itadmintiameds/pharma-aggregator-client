Compute

Two compute types cover the whole system, split by traffic shape rather than convenience — see the Decisions section of Search Service for the reasoning this pattern comes from.

Amazon ECS on Fargate
compute · serverless containers Active
Seller User Buyer User Order Mgmt Quotation Mgmt Billing Mgmt Product Mgmt Search (query layer)

The default for anything needing a warm process — a live connection pool to Aurora, low-latency request handling, or steady background load. No servers to patch, no idle-capacity waste at this traffic level.

AWS Lambda
compute · event-driven functions Active
Notification Service Search (index consumer)

Reserved for work that's bursty and idle most of the time — a catalog change, a notification send. Paying for an always-on Fargate task here isn't justified; Lambda scales to zero between bursts.

Database & caching

Transactional services get a single-writer Aurora cluster each (per ADR-007); Product Management is the one exception, running active-active because it's read-heavy and lag-tolerant.

Amazon Aurora PostgreSQL
database · single-writer cluster, one per service Active
Seller User Buyer User Order Mgmt Quotation Mgmt Billing Mgmt

Relational, transactional correctness where it actually matters — orders, payments, registrations. Single-writer with a warm standby, never active-active, because these five are the write-sensitive services per ADR-007. Billing runs a physically separate cluster from Order — enforcing the no-duplication rule (ADR-004) at the infrastructure level, not by convention.

Aurora Global Database
database · active-active reads across regions Active
Product Management

The one write-heavy-but-read-tolerant domain. One write primary, but read replicas fan out globally — the exception to single-writer specifically because Product Management is 59% of the system's tables and almost entirely read traffic.

Amazon ElastiCache (Redis)
database · in-memory cache Active
Product Management

Sits in front of Aurora specifically to absorb high-volume browse/catalog-read traffic without hitting the writer. No other service gets this treatment — no other service has Product's read volume.

Amazon OpenSearch Service
database · managed search index Active
Search Service

Purpose-built full-text/faceted search. No other service touches it — it's a disposable index rebuilt from Product's events (ADR-005), never a source of truth. Managed snapshots and zone-aware replicas remove exactly the operational surface a search cluster otherwise demands.

App integration & messaging

Async-by-default (ADR-003) runs on EventBridge + SQS everywhere except one flagged edge — see ADR-009 for exactly when that changes.

Amazon EventBridge
app integration · event bus Active
Order → Billing Order → Notification Billing → Notification Product → Search

The async backbone for everything per ADR-003 — fan-out to independent consumers with no cluster to run, no polling. The default for every edge unless a specific edge needs ordering or replay that EventBridge can't give.

Amazon SQS
app integration · queue, behind every consumer Active
Every async consumer

Retry and dead-letter handling behind every EventBridge target — the missing piece named explicitly in ADR-009 so "async by default" doesn't silently drop failed deliveries.

Amazon SNS
app integration · SMS delivery Active
Notification Service

SMS fan-out from the one service that never receives a synchronous call by design — Notification only subscribes to events, it exposes no internal REST endpoint at all.

Amazon SES
app integration · email delivery Active
Notification Service

Email delivery — order confirmations, invoice notices — fired asynchronously from Billing/Order events, never on a critical path.

Amazon MSK (Kafka)
app integration · flagged, not adopted Candidate
Product → Search (candidate)

The only edge in the system flagged for ordered, replayable delivery — Search's index-backfill replays this exact stream, and EventBridge doesn't guarantee per-key ordering. Named in ADR-009 so it isn't lost, evaluated once real volume is measured — not adopted preemptively, and not applied system-wide.

Why not Kafka or RabbitMQ everywhere: most async edges here are simple fan-out with no ordering or replay requirement — running a managed Kafka cluster for those adds real operational cost with no matching benefit. RabbitMQ was considered and rejected outright: nothing in this system needs AMQP-style exchange/topic routing beyond what SQS already provides. See ADR-009 for the full reasoning.

Platform & management

Config and Discovery sit underneath every service, not on the client request path — every choice here traces back to one rule: the backend already deploys via ECS/ECR, so pick whatever integrates with that natively (ADR-002).

AWS Cloud Map
management · service registry Active
Discovery Service

Registration, health checks, DNS-based resolution for every service. Chosen over self-hosted Eureka/Consul specifically because it integrates natively with ECS — no new cluster to run per region, per ADR-002.

AWS AppConfig
management · live config, no redeploy Active
Config Service

Per-service, per-environment, per-region config with a refresh event instead of polling — this is the specific mechanism that makes the one-click region rollout in ADR-006 work without touching running services.

Systems Manager Parameter Store
management · plain config values Active
Config Service

Plain (non-secret) config values that AppConfig profiles reference — kept distinct from Secrets Manager below as a deliberate security boundary, not an accident.

Security & identity

AWS Secrets Manager
security · credentials, never in Config Service Active
Config Service (boundary) Every service with credentials

A deliberate boundary stated explicitly in config-service.html — secrets never live in Config Service's own store. Separating "config" from "credentials" is a security decision, not an oversight.

AWS IAM
security · roles & permissions Active
Every service (execution roles)

Execution roles for Lambda, cross-service permission boundaries — referenced explicitly in Notification's Terraform, implicit in every other service's task role.

Networking & client-facing edge

Amazon API Gateway
networking · sole client entry point Active
API Gateway service

Managed auth, rate-limiting, and routing out of the box. No domain service is directly reachable from the internet — every client request passes through here, per ADR-008. Service-to-service calls bypass it entirely, resolving via Cloud Map instead.

Amazon Route 53
networking · latency-based routing Active
API Gateway (multi-region)

Routes clients to the nearest regional gateway. Supports the "one API Gateway per region" call in api-gateway.html — keeps the region-add story a single parameterized deploy instead of a shared global resource to coordinate.

Amazon S3
storage · onboarding documents Active
Seller User Buyer User

Onboarding document uploads — I/O-heavy, not CPU-heavy, which is also why these two services scale on request-queue depth rather than CPU utilization.

Developer tools

Amazon ECR
developer tools · container registry Active
Every service (build→ECR→deploy)

Every container image lands here before deploy — the existing build→ECR→ECS pipeline the backend already runs, referenced in every service's Terraform build-time section.
