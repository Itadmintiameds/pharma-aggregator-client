Part one

Architecture Decision Records

Nine decisions that shaped the v0.2 service split — what was decided, what it beat, and the trade-off accepted in exchange. Each links to the service section(s) it governs, further down this same document.

ADR-001 · Accepted

Service boundaries, v0.2

Adopt 11 services — Seller User, Buyer User, Order Management, Quotation Management, Search Service, Product Management, Billing Management, Notification Service, API Gateway, Config Service, Discovery Service. Master/reference data stays a shared module, not a numbered service.

Context: v0.1 proposed 5 coarse domain services. Stakeholders want finer granularity to scale Order, Quotation, Billing, and Search independently, plus explicit platform services instead of implied infrastructure.

Alternatives considered: Keep v0.1's 5-service split; or split further per product category (rejected — no evidence of independent scaling need per category, and it would fragment a self-contained domain for no operational benefit).

Trade-offs: More services to deploy, monitor, and secure individually, in exchange for independent scaling and clearer team ownership per capability.

Consequences: Requires the platform layer (Gateway/Config/Discovery) to be operational before any domain service split delivers value — sequence platform-first in the migration roadmap.

Governs: Seller User, Buyer User, Order Management, Quotation Management, Search Service, Product Management, Billing Management, Notification Service

ADR-002 · Accepted

Discovery & Config: AWS-native over self-hosted

Use AWS Cloud Map for discovery and AWS AppConfig + Systems Manager Parameter Store for config, both provisioned per region via the same Terraform module.

Context: One-click multi-region requires services to find each other and get region-correct config without manual wiring.

Alternatives considered: Netflix Eureka + Spring Cloud Config Server; HashiCorp Consul. Both are natural fits for a Spring Boot team, but each is a stateful cluster to run, patch, and replicate per region.

Reason: The backend already deploys via ECS/ECR — Cloud Map integrates with ECS service discovery natively, with no extra cluster to run per region.

Trade-offs: Ties discovery/config to AWS; acceptable since compute, data, and CI/CD are already AWS-committed.

Governs: Config Service, Discovery Service

ADR-003 · Accepted

Sync vs async: default to async

A call is synchronous only when the caller cannot return a correct response without the result in the same request (Order↔Product stock/price check, Quotation↔Order creation on accept). Everything else — Billing, Notification, Search indexing — is event-driven over EventBridge.

Context: Cross-service coupling risk grows with every synchronous call added.

Alternatives considered: Sync everywhere (simpler to reason about, but couples the availability of every service to every caller); async everywhere (adds latency/complexity where a real-time answer is genuinely required).

Trade-offs: Async paths need idempotent consumers and a dead-letter queue per consumer; sync paths need circuit breakers so a slow Product Management doesn't cascade into failed orders.

Governs: Order Management, Quotation Management, Billing Management, Notification Service, Product Management

ADR-004 · Accepted

Billing owns no Order data copies

Billing's schema stores order_id as a foreign reference only. It's created from an OrderConfirmed event carrying just order id, buyer id, and total; any line-item detail needed for invoice rendering is fetched synchronously from Order Management at render time, never persisted in Billing.

Context: Explicit requirement: Billing must not duplicate Order Management's data.

Alternatives considered: Full data copy via CDC (rejected — reintroduces the duplication being avoided); a shared database/schema (rejected — violates service data ownership and makes the boundary unenforceable).

Trade-offs: Invoice rendering has a runtime dependency on Order Management being reachable; mitigate with a short-TTL cache on the line-item lookup, not a persisted copy.

Governs: Billing Management, Order Management

ADR-005 · Accepted

Search Service owns an index, not source data

Search Service has no source-of-truth tables — it maintains an OpenSearch index rebuilt from ProductChanged events published by Product Management.

Context: Search needs to scale independently of Product Management's write path.

Alternatives considered: Query Product Management's DB directly for search (rejected — couples search query load to the transactional catalog DB); Product Management embeds search itself (rejected — different scaling profile, per ADR-001).

Trade-offs: Search results are eventually consistent with catalog changes — acceptable for browse/search, not used for stock/price truth (Order still calls Product Management directly for that).

Governs: Search Service, Product Management

ADR-006 · Accepted

One-click multi-region via parameterized IaC

One Terraform module per service, region passed as a variable, remote state isolated per region; the existing GitHub Actions pipeline gains a region workflow_dispatch input instead of being duplicated per region.

Context: Requirement: adding a region should be a single scripted action, not manual per-service setup.

Alternatives considered: Manually provisioned regions (rejected — doesn't meet the one-click requirement and is error-prone at 11 services); a full orchestration platform like AWS Control Tower/Landing Zone (deferred — justified once region count grows past a handful, not needed for the first additional region).

Trade-offs: Requires discipline that nothing is provisioned by hand outside Terraform — any manual change in one region silently diverges from the module and breaks repeatability.

Governs: API Gateway, Config Service, Discovery Service — all services, per module

ADR-007 · Accepted

Single-writer regions for Order, Billing, Seller/Buyer User, Quotation; active-active for Product, Search, Master Data

Transactional/write-sensitive services (Order, Billing, Seller/Buyer User, Quotation) run single-writer with a warm standby region. Read-heavy, lag-tolerant services (Product Management, Search's OpenSearch index, Master/Reference Data on DynamoDB Global Tables) run active-active across regions.

Context: Aurora PostgreSQL Global Database supports one writer region at a time; true multi-writer needs a different data model entirely.

Alternatives considered: Force everything active-active via DynamoDB (rejected — Order/Billing need relational transactions and strong consistency a key-value multi-writer store doesn't give for free); force everything single-writer (rejected — throws away the real multi-region win for the read-heavy services).

Trade-offs: A regional outage in the primary write region means a controlled Aurora promotion (seconds-to-minutes RTO) for Order/Billing, not instant failover — accepted in exchange for payment/order correctness.

Governs: Order Management, Billing Management, Seller User, Buyer User, Quotation Management, Product Management, Search Service

ADR-008 · Accepted

API Gateway is the only client-facing entry point

Amazon API Gateway fronts all client traffic; no domain service is directly reachable from the internet. Service-to-service calls (Order→Product, Quotation→Order) go direct via Cloud Map resolution, bypassing the gateway.

Context: 11 independently deployable services need one consistent place to enforce auth, rate limiting, and routing rather than each reimplementing it.

Alternatives considered: Self-hosted Spring Cloud Gateway on Fargate — kept as a fallback option if routing needs (e.g. complex request transformation) outgrow what managed API Gateway supports.

Trade-offs: API Gateway becomes a single dependency for all client traffic — mitigated by AWS's own multi-AZ SLA, and by keeping service-to-service calls off this path entirely so an internal domain issue doesn't compound with a gateway issue.

Governs: API Gateway, Discovery Service

ADR-009 · Accepted

Event backbone: EventBridge by default, Kafka only where replay/ordering/volume demand it

Every async edge in the communication matrix (ADR-003) runs on Amazon EventBridge, with SQS behind each consumer for retry/DLQ handling, unless a specific edge needs one of the properties EventBridge doesn't provide — in which case that ONE edge moves to Amazon MSK (managed Kafka), not the whole system.

Context: EventBridge and SQS cover fan-out and task-queue semantics with no cluster to run, matching ADR-002's AWS-native bias. But EventBridge does not guarantee per-key ordering, its Archive/Replay path is a slow, ops-triggered recovery tool rather than a routine replay mechanism, and its per-event pricing/throughput has a practical ceiling.

Decision — the four triggers. An async edge graduates from EventBridge to Kafka (MSK) only when it needs at least one of:

  1. Ordered replay is a correctness requirement — out-of-order delivery silently corrupts state (not just delays it).
  2. Routine replay-from-any-offset is part of normal operation, not disaster recovery — e.g. rebuilding a derived store from scratch.
  3. Multiple independent consumer groups need to read the same stream at their own pace with their own offsets, without N hand-wired EventBridge targets.
  4. Sustained volume exceeds EventBridge's cost/throughput curve — measured, not assumed.

Where this applies today: the Product Management → Search Service edge (ProductChanged) is the only edge in the current service catalog that plausibly hits triggers 1 and 2 — see Search Service §02. This edge is flagged as a Kafka candidate, evaluated once real event volume is measured — not switched preemptively.

Alternatives considered: RabbitMQ — rejected for now, nothing in the current catalog needs exchange/topic routing beyond SQS. Kafka everywhere — rejected as premature; most edges are simple fan-out with no ordering/replay need.

Trade-offs: A mixed backbone means two operational models instead of one — accepted because forcing every edge onto the hardest edge's technology is the more expensive mistake. Revisit per-edge, not system-wide.

Governs: Search Service, Product Management, Order Management, Billing Management, Notification Service

01 · Domain service

Seller User Service — schema consolidation and deployment topology

What Seller User owns today across three parallel entity packages, how those collapse into one service schema, and why this service sits in the single-writer bucket rather than active-active.

01

Overview

Seller User owns the seller's identity end to end: profile, registration, onboarding documents, bank details, and the seller/coordinator auth surface that Order, Quotation, and Product all lean on to answer "is this seller allowed to act." Nothing about a seller's catalog or transactions lives here — only who they are and whether they're approved.

Traffic is bursty rather than steady: registration and document upload spike around onboarding windows and go quiet in between. Document upload in particular is I/O heavy, not CPU heavy, so it scales on request queue depth, not CPU utilization.

02

03 · Domain service

Order Management — the strict-consistency core of the order lifecycle

Why Order stays single-writer while everything around it scales out, what has to physically move out of its package before Billing can be its own service, and how quote acceptance, price checks, and event fan-out fit together.

01

Overview

Order Management owns orders, order lines, order status transitions, and returns/refunds. This is the one service where correctness has to win over horizontal write scaling.

Double-charging a buyer, losing a status transition, or accepting an order against stock that no longer exists is not a data-quality problem, it's a financial and regulatory one. Order Management is deliberately single-writer and strongly consistent even though that costs active-active write scaling.

02

Data ownership

The entity/order package shows 8 tables: tbl_order, tbl_seller_order, tbl_order_item, tbl_order_status_history, tbl_return_request, tbl_refund, tbl_payment, and tbl_invoice.

The first six are squarely Order's: an order splits per seller since a single buyer cart can span multiple sellers, every status change is journaled rather than overwritten, and returns/refunds get their own tables.

Flag — tbl_payment and tbl_invoice are misplaced today: both currently live inside Order's package. This is a required physical migration into Billing's own schema and cluster before Billing can be extracted. See Billing Management §02 and ADR-004.
03

Communication

Order sits at the center: one sync call in from Quotation, one sync call out to Product, two async event streams to Billing and Notification.

Sync IN Quotation Management → Order

create-order-on-accept
  • When a buyer accepts a quote, Quotation calls Order to create the order before returning "accepted."
  • The order references the quote by ID; nothing is copied into Order's tables.

Sync OUT Order → Product Management

price/stock confirmation on order creation

04 · Domain service

Quotation Management — negotiation state and the single-table problem

Why one table backing two flows and three cross-domain foreign keys is a bigger problem than it looks, and how the negotiation trail should actually be modeled once this becomes its own service.

01

Overview

Quotation Management owns buyer quote requests, seller quote responses, and the negotiation state that sits between them — the pre-sale conversation that either dies quietly or converts into an Order.

Traffic tracks B2B negotiation cycles: quiet stretches interrupted by clusters of activity when a buyer organization is actively sourcing.

02

Data ownership

Exactly one table in entity/quote today: tbl_quote_request. No separate seller-response table, no separate negotiation-state table.

That one table backs both quoting flows — "Request Price Option" and RFQ "Get a Quote" — discriminated by a requestType enum.

Open architecture question, answered as a decision: a single mutable row overwritten on every back-and-forth loses the negotiation trail. Recommendation: a companion tbl_quote_negotiation_history table that appends one row per exchange.

Second flag — three-way cross-domain foreign keys: today's QuoteRequest entity directly foreign-keys BuyerUser, Seller, and ProductDetails. That breaks the moment those become separate service databases — the target service has to store opaque IDs and resolve via API calls.

03

Communication

Quotation makes two outbound synchronous calls and receives none.

Sync OUT Quotation → Product Management

pricing lookup during quote generation
  • The buyer needs to see an actual number, not a stale indexed one.

Sync OUT Quotation → Order Management

create-order-on-accept
  • The order must exist before the acceptance response goes back to the buyer.

05 · Domain service

Search Service — build-time vs. deployment-time infrastructure

Where OpenSearch gets built, what Terraform provisions once versus per-deploy, and the AWS wiring that keeps the index disposable and the query path cheap.

01

Why this needs a build/deploy split at all

Search Service owns no source data — it's a query layer over an OpenSearch index rebuilt from ProductChanged events. The index schema and mapping is a build-time artifact; the index's data is a runtime artifact rebuilt continuously and disposable.

02

Build-time: what CI produces

Build Query-layer image

on every merge to main
  • Compile the stateless query service into one container image.
  • Tag with commit SHA, push to ECR.

Build Index template & mapping

versioned alongside the consumer code
  • A mapping change ships as a new index version (products-v13), never a mutation of the live index.
  • CI validates the mapping against a sample document set before merge.
Why version the index name, not the domain: reindexing safely means writing to products-v13 while products-v12 still serves traffic, then flipping an alias.
EventBridge vs. Kafka for this edge, specifically: backfill works by replaying ProductChanged in order — EventBridge doesn't guarantee that. This is the one edge in the system flagged as a Kafka (MSK) candidate — see ADR-009.

06 · Domain service

Product Management — the catalog of record and the cost of splitting it out

What Product Management owns today, how it's read by nearly every write path elsewhere, and why extracting it is the single biggest cross-cutting migration risk in the whole decomposition.

01

Overview

Product Management is the catalog of record for every sellable item — Drug, Consumable, Non-consumable, Supplement, Cosmetic, and Food/Infant, plus shared lookup masters.

Reads dominate by a huge margin, writes are comparatively rare. It's also the single largest domain by table count in the entire system.

02

Data ownership

07 · Domain service

Billing Management — extracting invoicing without duplicating Order's data

Why Billing is a migration target rather than a greenfield service, why its database has to be physically separate from Order's, and how it renders invoices without storing a second copy of an order's line items.

01

Overview

Billing Management owns invoices, payment records, and ledger entries. It references orders by order_id and stores no copy of any order's line items.

Traffic is spiky, concentrated hard around reconciliation and month-end close.

02

Data ownership

Zero dedicated tables exist for Billing today. Payment (tbl_payment) and Invoice (tbl_invoice) currently live inside Order's package.

Standing up Billing means extracting two existing tables out of Order's package, plus adding a ledger_entries table that doesn't exist yet.

Why the migration has to be physical: the tables must move to Billing's own schema and cluster so that no query can join Billing data against Order's tables directly — see Order Management §02.
03

Communication

Almost entirely reactive: one async inbound stream from Order, one on-demand sync call back to Order, one async outbound stream to Notification.

Async IN Order Management → Billing

OrderCreated / OrderStatusChanged via EventBridge
  • Billing can lag behind Order by seconds without the buyer noticing.

Sync OUT Billing → Order Management

line-item lookup, at invoice-render time only
  • Used to render the invoice and then discarded — never persisted.

Async OUT Billing → Notification Service

InvoiceGenerated / PaymentFailed events
  • Fire-and-forget, consistent with the platform-wide rule.
04

Architecture diagram

sync (blocking) async (event)
05

Deployment

ECS Fargate with bursty autoscaling for month-end spikes, Aurora PostgreSQL physically separate from Order's.

Single-writer with warm standby, per ADR-007, with autoscale burst capacity layered on top for month-end volume.

08 · Domain service

Notification Service — async-only by construction, not convention

The smallest service in the system by data footprint, and the one with the strictest architectural rule: nothing is allowed to call it synchronously, and the deployment shape makes that structurally true.

01

Overview

Notification Service holds no persistent business data — at most a delivery log. Fully event-driven end to end, scales to zero between bursts.

One rule governs everything: it must never be called synchronously by another domain service. Notification delivery depends on third-party providers (SES, SNS) whose latency is outside the platform's control.

02

Data ownership

Zero entities or tables today. 100% greenfield.

Proposal, not existing fact — a delivery log, if added, should be a single append-only table:

CREATE TABLE notification_log (
  id          uuid PRIMARY KEY,
  recipient   text,
  channel     text,
  template    text,

Every inbound call is asynchronous. There is no synchronous inbound path, by design.

Async IN Order Management

order confirmation

Async IN Billing Management

InvoiceGenerated / PaymentFailed
